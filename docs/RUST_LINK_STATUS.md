# Rust / Blender link status

Updated 2026-10-17 (embedded networks); previously 2026-10-16. This describes the current checkout, including the add-on changes here. The Desktop backup was not changed.

## Blender Object pickers, waiting state, object-name search (add-on 0.5.0)

Every `blender_object` node in a bound graph is an implicit object input: interface entry `{"node":"@picker",
"id":<stable id>,"kind":"object","implicit":true}`, source key `input:@picker:<id>`, fed to the core as
`picker:<node>`. External-data nodes with nothing to read yet are *waiting* (`CookStats::waiting`, `cook.waiting`
in instance results), not errors. The add-on hello advertises `object_names_v1`; the app sends
`object_names_query` only while the Blender Object node's name field is edited and the add-on answers
`object_names` with at most 50 ranked matches, scanned time-sliced on its main thread. Details and timings:
[BLENDER_OBJECT_NODE.md](BLENDER_OBJECT_NODE.md).

## Viewport materials and image assets (add-on 0.4.0)

The native welcome advertises `viewport_materials_v1` and `image_assets_v1`. Watched objects, stack modifiers, Geometry Nodes placements and their `instance_sources` can send revisioned material manifests. The app requests missing SHA-256 image payloads and verifies bounded MHL1 `|u1` chunks before rebinding the existing material registry. Descriptor changes refresh GPU texture bindings without a geometry recook. Older peers retain untextured geometry. Missing images show the viewport checker; unsupported material node paths show a diagnostic and retain their constant factor. See [TEXTURE_TRANSPORT.md](TEXTURE_TRANSPORT.md) for exact messages, limits, tests, and open gaps. The native interactive viewport has not been smoke-tested with a live Blender window in this run.

## Dynamic modifier inputs (add-on 0.2.0)

The Rust `modifier_input` node stores ordered `modifier_inputs` definitions (`id`, `name`, `kind`, `default`, optional `min`, `max`, `subtype`, or menu `options`). The native params panel adds them. `link_interface` advertises every definition; `instance_cook` applies per-placement values to `input_values` before graph evaluation. A node parameter can bind to `{"modifier_input":{"node":"input","id":"input_1"}}`; the Rust graph resolves that value during cook, so existing numeric/string node parameters consume it without a new scalar-port evaluator. The add-on maps stable IDs to Blender socket identifiers, preserving modifier values and GN wires through rename/reorder. Removed inputs are removed cleanly. Independent instances keep separate values.

The 0.2.0 bridge lists float, int, bool, vector, color, rotation, matrix, string, menu, object, collection, material, image, texture, geometry, bundle and closure socket types. Float, int, vector and string subtypes map to their matching Blender socket classes; vector includes translation/xyz/euler/direction/velocity/acceleration. `bpy.app.version` and available `bpy.types` guard newer sockets. Menu inputs connect to generated Menu Switch nodes so Blender can populate their options; a new menu defaults to its first option. Rotation and matrix use the modifier's attribute-use chain, while object, collection, material, image and texture use reference comparisons on Blender 5.2+. Object and collection references cross as names; evaluated object meshes travel through `instance_sources`, with names/transforms in `references`. Wired geometry inputs also travel as mesh sources. Existing `object_input` nodes can read an `input:<modifier node>:<stable id>` binding. Material/image/texture references are available as names to string-accepting Rust nodes. Linked bundle/closure values report an unsupported-data error. Computed links beyond float/int/bool/vector sampling have not been implemented; unsupported computed links report an error instead of being guessed.

Mocked bpy interface tests and the headless Rust link test cover float, int, bool, vector, color, string and object round trips, independent placement values, and stable socket identifiers on rename/reorder. Actual Blender socket construction, modifier panel behavior, evaluated object/geometry sampling, reference metadata and UI interaction remain unverified without Blender.

## Embedded networks (add-on 0.3.0, `graph_embed_v1`)

The welcome now also advertises `graph_embed_v1`. `graph_push` -> `graph_ack` (unchanged / accepted / app_newer / conflict) and `graph_pull` -> `graph_state` (ok / none / pending / resolved) carry an embedded network as exact JSON text with a sha256 over its bytes, a byte size (max 32 MiB) and envelope schema 1; `instance_synced` adds `hash` and `embed_pending`. The app binds a document titled `Blender: <object>/<modifier>`, asks in an egui modal when Blender's copy and app edits (or an unsaved open document) conflict, and its Save As on a bound document exports a `.minihou` copy without unbinding. Instance graphs may be `.minihou` files. Pending conflicts and answers are shared across connections so a reconnecting add-on still learns the outcome. Older add-ons/apps keep working: the add-on only pushes when the capability is present. Pure logic: `src/graph_embed.rs`; handling: `link_instances.rs` (`embed_push`/`embed_pull`), `blender_link.rs` (`live_replace`, `resolve_embed`), `main.rs` (modal). Evidence: Rust unit tests, and `tests/test_blender_embed.py` against `link_selftest` in headless Blender 4.3, 5.0, 5.1 and 5.2 (the selftest accepts `open_dirty` and `resolve` control commands). The app's modal and title have not been exercised in the live window. See [EMBEDDED_GRAPHS.md](EMBEDDED_GRAPHS.md).

## Blender-side input definitions (add-on 0.3.1, `input_define_v1`)

The welcome also advertises `input_define_v1`. Blender sends `{"type":"input_define","request_id","instance_id","path","op":"add"|"rename"|"remove","node"?, "input":{name,kind,default?,min?,max?,subtype?,options?,doc?} | "id","name"}` (header at most 64 KiB) on the instance connection; it is forwarded to the UI thread and always answered with `input_define_ack` carrying the same `request_id`/`instance_id`: `status:"ok"` with `input` (the stored definition incl. node and stable id), the full `graph` and its `interface`, or `status:"error"` with `code` `not_bound` (the network is not the document bound in the app: the live modifier's path, or the open file's path when nothing is live), `invalid` (refused, in the same words as the app's Add input) or `busy`. The app applies it as one undoable `Edit::ModifierInputs` (`input_define::handle`), using `input_define::add_entry` -- the same function the app's **Add input** button now uses (ids `input_N`, name suffix ` 2`, ` 3`... against all input and exposed names, reserved Blender names, validation). Fallbacks in the add-on: `not_bound`, no app, or an older app without the capability -> the definition is applied by the Python mirror of those rules (`blender_addon/minihou_link/input_define.py`) to the embedded graph text (authoritative in Embedded mode; the app sees it on the next Edit Network / graph_push); the older-app case is reported as a warning ("the connected MiniHou app cannot define inputs"). Linked File networks need the bound app (the file is MiniHou's to write) and say so. Code: `src/input_define.rs`, `blender_link.rs` (routing, `reply`, `bound_path`), `main.rs` and `examples/link_selftest.rs` (handler). Evidence: Rust unit tests (plan/ack/error/size/undo/bound check, connection routing), mocked-bpy `tests/test_input_define.py`, and `tests/test_blender_input_define.py` against `link_selftest` in headless Blender 4.3, 5.0, 5.1 and 5.2. Not exercised: the popup dialog drawn interactively and the app window.

## Test host and reproduction

`rust/crates/minihou-app/examples/link_selftest.rs` reuses the production `blender_link.rs`, core evaluator, Document and History. It opens no window or GPU. It accepts `GRAPH.json ADDRESS SECONDS [CONTROL.json]`, binds an ephemeral port with `127.0.0.1:0`, prints `LINK_READY <actual address>`, and exits on its deadline or a stop control. The optional command file simulates native exposure/parameter/history edits for integration tests. It is an example executable, not a new desktop-app CLI mode.

`tests/test_rust_link.py` loads the actual bpy-free add-on client/protocol/state/instance-client/router/scene-plan files in an isolated package, avoiding the bpy-dependent add-on entry point. Each test starts its own debug Cargo example with temporary graph/control files and a temporary listener. It never finds, launches or kills a running desktop app. It uses no Python engine/server as a substitute for Rust.

From the repository root:

```powershell
$env:PATH = "$env:USERPROFILE\.cargo\bin;$env:PATH"
$env:CARGO_TARGET_DIR = Join-Path (Get-Location) 'rust\target_inst'
python -m unittest discover -s tests -p test_rust_link.py -v
python -m unittest tests.test_protocol tests.test_network_editor tests.test_scene_plan tests.test_scene_objects tests.test_images tests.test_geonodes_engine tests.test_modifier_instances -v
Set-Location rust
cargo test -p minihou-app --lib --example link_selftest
cargo test -p minihou-app --bin minihou-app ui::params::tests
cargo check -p minihou-app --all-targets
```

The targeted Rust test commands execute test harnesses; they do not run the desktop executable. Do not replace them with an unrestricted `cargo test -p minihou-app` when the desktop executable must not be invoked: existing `tests/cli.rs` explicitly runs it.

Results: eight Rust-server socket integration tests and 106 existing Python regressions pass. The final targeted Rust run passed 66 library tests, 14 example/server tests and all six params-panel tests (including the egui Expose-button test). `cargo check --all-targets` and syntax checks on all changed Python files pass. Logs are under `rust/target_inst/link-*.log` (local generated evidence, not a release artifact).

Validation caveat: an initial broad Cargo test run also ran the pre-existing CLI tests, which invoked `minihou-app.exe` with `--selftest` despite the requested restriction. No window was opened. Subsequent/final runs use only the targeted commands above. No release build or Blender launch was performed.

## Remaining gaps / unverified behavior

- **No live Blender acceptance:** actual socket creation/removal, modifier-stack prefix evaluation, wired/nested GN evaluation, Blender material/data-block updates, scene-object/image realization, undo UI, depsgraph feedback behavior, and native window focus have not been smoke-tested in Blender. The egui test proves control dispatch and saved exposure state, not Blender socket creation. No claim of host-app acceptance is made.
- **Shared memory:** deliberately unimplemented and unadvertised. TCP fallback is tested with both add-on clients. Large-geometry throughput and interactive latency are unbenchmarked.
- **Rust graph support:** protocol parity does not add Python-only nodes, Python node-library execution, arbitrary attribute dtypes, or unsupported core node parameters. The add-on mesh readers already convert generic booleans to int32; core geometry attributes support float32/int32, with byte/bool topology flags. Unsupported cases return explicit errors. In particular, the optional non-empty `image_out.file` PNG side effect remains unsupported by the Rust core; network image exchange works.
- **Native presentation:** native live editing uses temporary independent JSON documents rather than the Python HTTP/browser editor. The TCP welcome has no browser `editor_url`. The generic Start Server/Open Browser controls still belong to the existing Python server-control workflow; this work enables the live modifier/GN native route. Native preview currently shows core instance-point geometry rather than Python's source-mesh realization preview. These presentation differences do not change geometry sent back to Blender.
- **Proxy policy:** Rust sends its cooked geometry; Python's adaptive cook-proxy policy is not ported by this change. The native viewport's display LOD remains a separate feature. No shared-memory or adaptive-proxy capability is claimed.
- **Side-output diagnostics:** the current `CookResponse` exposes a single aggregate error string for proxy-side extra/sink failures, so the last such error is what the TCP proxy error reports. Valid main/other successful outputs still flow. Instance replies have separate per-node `scene_errors`.
